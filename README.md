# ML Incident Prediction Platform

Сервис оценивает вероятность инцидента в ближайшие 10 минут по последним 10 минутам метрик
(CPU %, память %, доля ошибок 5xx %, p95-задержка мс), берёт метрики из Prometheus и шлёт оповещение в Telegram.

## Быстрый старт
```
python -m venv .venv && .venv\Scripts\activate        # Windows
pip install -r requirements.txt
python -m training.train                               # обучение + отчёт, создаёт model/
pytest                                                 # тесты
uvicorn api.main:app_factory --factory --port 8000
```
Docker: `docker compose up --build` (API :8000, Prometheus :9090, node-exporter для реальных CPU/памяти).

## API
`POST /predict` — тело `{"samples": [{"cpu":..,"memory":..,"error_rate":..,"latency":..}, ... не меньше 10 ...]}`
(по замеру в минуту, от старых к новым). `GET /model` — параметры и отчёт об оценке, `GET /health`, `GET /metrics` (для Prometheus).

## Боевой режим
Если задан `PROMETHEUS_URL`, раз в минуту сервис сам берёт 4 метрики, копит окно и считает риск.
Если заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` — шлёт сообщение, когда риск выше порога 2 замера подряд
(не чаще раза в 30 минут, затем сообщение о снижении риска). PromQL-запросы по умолчанию рассчитаны на node-exporter и
метрики `http_requests_total{status}` / `http_request_duration_seconds_bucket` — подстройте через `PROM_QUERY_CPU|MEMORY|ERROR_RATE|LATENCY`.
Единицы должны совпадать с обучением (проценты и миллисекунды).

## Что изменено по сравнению с первой версией
- API стартует: убран бесконечный цикл, вешавший импорт `api/main.py`.
- Исправлены сборка (`requirements.txt`, зависимость `prometheus-client`) и пустые заглушки (реализованы collector, features, schemas/routes, alerting, Telegram).
- Метка инцидента теперь про БУДУЩЕЕ, признаки — по ПРОШЛОМУ окну. Раньше метка считалась формулой от тех же 4 чисел, и модель лишь «угадывала формулу».
- Честная оценка: разбиение по времени (обучение → подбор порога → тест), сравнение с наивным правилом по ошибкам, метрики для дежурного (пойманные инциденты, ложные тревоги в сутки).
- Признаки считаются одним кодом для обучения и боя (тест на отсутствие train/serve skew и на «непросмотр будущего»).
- Модель хранится вместе с `metadata.json` (список признаков, порог, версия sklearn); несовместимая модель не загрузится.

## Результат на синтетическом тесте (хвост ряда, ~18 инцидентов)
Модель: precision 0.95, recall 0.57, поймано заранее 14 из 18, ложных тревог ~0.24/сутки.
Наивное правило «ошибки выросли»: precision 0.41, recall 0.26, ~3.3 ложных тревог/сутки.

## ВАЖНО: ограничения
- **Данные синтетические.** Предвестники (рост метрик перед сбоем) заложил генератор, 30% сбоев в нём внезапные. Цифры выше показывают, что пайплайн работает и не обманывает сам себя, но НЕ качество на вашем сервисе.
- Для реальной пользы нужна история ваших метрик из Prometheus и отметки реальных инцидентов; затем заменить `training/dataset.py` загрузкой этих данных (остальной код уже готов).
- `model/incident_model.joblib` — формат pickle: загружайте только свои файлы.
- Telegram и Docker проверены частично: Telegram и Prometheus — против локальных имитаторов HTTP-сервера, Docker-сборка в песочнице не запускалась.
